# BUG-0007: Concurrent set-default calls can leave a user with no default address (all return 200 `is_default: true`)

| Field | Value |
|---|---|
| Bug ID | BUG-0007 |
| Module | backend: `apps/accounts/services/addresses.py` (`set_default`, also `delete_address`), `apps/accounts/views.py` (`_own_address`) |
| Owner agent | `django-backend-dev` |
| Severity | **P2 Major** (brief scale: **Medium**). The data invariant "one default per user" breaks and the API reports success with a stale body. Workaround: set the default again. |
| Priority | P3 (low likelihood: the same user must send overlapping set-default requests, e.g. two devices or a double tap) |
| Status | Open |
| Found | 2026-11-02, QA run 1 (P1-TC-57 failed intermittently in the final regression run) |
| Environment | Commit `4960527`, QA instance `127.0.0.1:8004` (local settings), shared remote PostgreSQL |
| Test | `qa/tests/test_p1_addresses.py::test_p1_tc57_concurrent_default_changes` (xfail, non-strict: race) |

## Steps to reproduce
1. As a QA customer with 5 live addresses, send 10 concurrent `POST /api/v1/addresses/{id}/set-default/` requests (each of the 5 ids twice, 10 threads).
2. Count live defaults: `GET /api/v1/addresses/`, or read-only SQL `count(*) where is_default and not is_deleted`.
3. Repeat. Reproduced in **1 of 8** trials in a dedicated probe, and once in 1 of 4 full regression runs.

## Expected
03 §2.4 "One default per user". 06 §2.2: "`set-default` moves it". The services' own docstring: "Soft delete and exactly one default per user". After any sequence of successful set-default calls, exactly one live address is the default, and it is the one the last-committed request set.

## Actual
```
trial 2: statuses=[200] responses_claiming_default=10 live_defaults_in_db=0
trials with ZERO default: 1 of 8
```
All 10 responses are 200 and claim `is_default: true`, but the user ends with **zero** default addresses. (`qa/private/runs/bug0007-repro.txt`)

## Possible root cause
`AddressSetDefaultView.post` loads the address via `_own_address()` **before** the transaction and lock. `set_default()` then takes the user lock and decides with the stale in-memory flag:
```python
live_addresses(address.user).filter(is_default=True).exclude(pk=address.pk).update(is_default=False)
if not address.is_default:          # stale: read before the lock
    address.is_default = True
    address.save(update_fields=["is_default", "updated_at"])
```
Interleaving:
1. Request Y loads A1 while A1 is the default (stale `is_default=True`).
2. Request Z (A2) commits: A1 is unset, A2 is set.
3. Y gets the lock and unsets A2.
4. Y skips its save because its stale copy says A1 is already the default.
5. No default remains.

`delete_address()` has the same pattern (`was_default = address.is_default` read before the lock), so a concurrent delete and set-default can also lose the default.

## Suggested resolution
Inside the locked transaction, re-read the row: `address = Address.objects.select_for_update().get(pk=address.pk)`. Or unconditionally run `live_addresses(user).filter(pk=address.pk).update(is_default=True)` after unsetting the others. Do the same in `delete_address()`. Add a threaded backend test (`TransactionTestCase`), and keep QA P1-TC-57 as the black-box guard.
