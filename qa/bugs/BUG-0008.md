## Public summary
- 06 §2.3 says notify-me is "harmless to repeat (the server may merge duplicates)", and 09 §3.2 says customers only ever see their own data. 09 §3.3 says PII is minimised.
- When the server merges an **anonymous** repeat into an existing lead, the 201 response echoes the **stored** lead, not the caller's request. Under certain conditions the stored lead belongs to someone else, so another person's stored location details come back to an unauthenticated caller.
- Signed-in repeats are not affected: they only ever merge into the caller's own leads.

## Suggested direction
For merged anonymous requests, never return stored fields. Echo the caller's own submitted values, or answer with an empty or minimal body. Keep the de-duplication server-side only. Add a backend test in which two anonymous callers submit different text and each gets back only their own.

## Verification (2026-11-09, QA P5–P7 run, `4ac5dae`)
Fixed per 06 §2.3 ("an anonymous request is never merged"). Black-box on the QA instance: two anonymous notify-me requests with the same QA phone 50 m apart get **different** lead ids, and the second response echoes only its own `address_text` and coordinates. A signed-in user's repeat still merges into their own lead (same id). `tests/test_p2_serviceability.py::test_p2_tc18_notify_me_dedupe` (oracle updated: anonymous repeats are not merged) and the new `test_p2_tc18b_notify_me_signed_in_merge`: **2 passed**. With the fix verified, the summary above is now public; the exploit detail file no longer exists in `qa/private/`.
