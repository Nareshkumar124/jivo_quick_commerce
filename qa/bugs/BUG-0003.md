# BUG-0003: A refresh token can be redeemed several times when the requests are concurrent

## Steps to reproduce (summary)
1. Sign in with a QA test number to get a refresh token R.
2. Send several `POST /auth/token/refresh/ {"refresh": R}` requests at the same moment, from parallel connections.

## Expected
06 §2.1 and the schema say: "The refresh token sent is revoked, so it works exactly once". Exactly one request returns 200. All others return `401 TOKEN_INVALID` ("Token is blacklisted").

## Actual
All concurrent requests return 200, each with a **different** new refresh token. Every one of those is recorded as outstanding and is itself usable, so one refresh token becomes several independent 30-day sessions. Sequential reuse is correctly rejected (P1-TC-24 passes).

## Evidence
```
successes 10 distinct 10 statuses [200 x10]
outstanding rows for forked tokens: 10
blacklist rows for original: 1
forked refresh tokens each usable once more: 10
```
(10 parallel requests against the QA instance; read-only SQL on `token_blacklist_*`.)

## Possible root cause
simplejwt 5.5.1 `TokenRefreshSerializer.validate()` checks the blacklist (`check_blacklist`, an `exists()` query), then later blacklists with `get_or_create` and issues a new token. These steps are not atomic and not locked, so concurrent requests all pass the check before any of them writes the blacklist row. The project uses the stock view: `apps/accounts/views.py` `TokenRefreshView(SimpleJWTTokenRefreshView)`.

## Suggested resolution
Make redemption atomic. For example, use a custom refresh serializer that, inside `transaction.atomic()`:
- locks the `OutstandingToken` row (`select_for_update()`) for the token's `jti`
- or inserts the `BlacklistedToken` first and treats an `IntegrityError` or an existing row as "already used" (401)

Only then mint the new pair. Add a concurrency test using threads or `TransactionTestCase`. Optionally, apply reuse detection: when a blacklisted token is presented again, revoke the whole user's outstanding tokens.

## Security impact (was private until the fix)

Fire N parallel `POST /api/v1/auth/token/refresh/` requests with the same refresh token, for example 10 threads with independent HTTP connections. All N return 200 with distinct refresh tokens, giving N parallel session families. Logging out one family (`/auth/logout/` revokes only the token given) leaves the others alive for up to 30 days. Only "revoke all", which runs on account deletion and on a Customers-admin block, catches them all, since each forked token is recorded in `OutstandingToken`.

Stealthy persistence scenario: an attacker who briefly obtains a victim's refresh token forks it into many sessions in one burst. The victim's own app keeps working, because one of the forks may be the victim's next rotation, so nothing signals the compromise.

## Verification (QA run 2, 2026-11-03)
**Build:** `develop` at `0b801d1`, on QA instance `127.0.0.1:8004` (local settings).

**Fix:** `apps/accounts/services/auth.py` `rotate_refresh_token()`. The view no longer uses simplejwt's stock serializer. Inside `transaction.atomic()`, redemption runs `BlacklistedToken.objects.get_or_create(token=<the token's OutstandingToken row>)`. Only the request that creates the blacklist row mints the new pair; the others raise `TokenError("Token is blacklisted")`, which becomes 401 `TOKEN_INVALID`.

**Evidence:**
- The strict xfail guard turned XPASS: `[XPASS(strict)] BUG-0003: concurrent refreshes all succeed (race)` (`qa/private/runs/run2-private-guards.txt`).
- Repeated 10-way races (`qa/tools/race_trials.py refresh N`), each with a fresh login for QA user A:
```
local PostGIS fallback (run2-race-trials-localdb.txt):
  trial 00..19: successes=1/10 losers_401_TOKEN_INVALID=9 other_statuses=0
  SUMMARY refresh: 20/20 valid trials correct, 0 failed, 0 environment errors
remote shared DB (run2-race-trials.txt):
  11 trials: successes=1/10 in every trial; 3 trials had 1-4 losers answered 500 instead of 401.
  Every 500 in the instance log is psycopg ConnectionTimeout (remote DB connect > 5 s, OBS-01);
  no IntegrityError, deadlock or second success.
```
- `test_p1_tc24c` (5 trials per suite run) also checks with read-only SQL that the user's `token_blacklist_outstandingtoken` count grows by exactly 1 per race, and that the winner's new refresh token works once more.
- The sequential reuse case (P1-TC-24) still returns 401 `TOKEN_INVALID`.

**Residual:** under remote-DB connect timeouts a losing request can return 500 instead of 401. The token is still single-use, because the 500s never mint a token. This is OBS-01 (pooling, or 503 for DB-unavailable), not this bug.
