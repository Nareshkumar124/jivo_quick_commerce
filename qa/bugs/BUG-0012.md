# BUG-0012: Dispatch crashes outside test settings, so no rider is ever offered an order

| Field | Value |
|---|---|
| Bug ID | BUG-0012 |
| Module | backend: delivery dispatch (`apps/delivery/services/dispatch.py` `_later`) |
| Owner agent | `django-backend-dev` |
| Severity | **P0 Blocker** (brief scale: **Critical**). The main P5 workflow (order → offer → delivery) doesn't work in any real environment. |
| Priority | P0 |
| Status | **Verified** (fixed in develop `f5d39ff`, verified 2026-11-06) |
| Found | 2026-11-06, QA Phase 5 stage 2 |
| Environment | develop `999ef38` (slice 5.3 merged, `delivery.0002` applied), QA instance `127.0.0.1:8004`, `config.settings.local`, QA Celery worker on Redis DB 7 |
| Test | `qa/tests/test_p5_dispatch.py::test_p5_tc39_accept_reveals_address_idempotent` (and every 5.3 flow case) |

## Steps to reproduce
1. Run the backend and a Celery worker with any non-test settings (`config.settings.local`, staging or production).
2. Make QA rider R1 (+919000000103) ACTIVE at QA-02 and online (`shift/start` plus a location point at the store).
3. Customer A places a COD order at QA-02. Auto-accept moves it to ACCEPTED.
4. Poll `GET /api/v1/rider/offers/current/` for 25 s.

## Expected
08 §5 (dispatch): on ACCEPTED, a DeliveryTask is created and the eligible rider gets an offer within seconds (P5-TC-34/39).

## Actual
No offer ever arrives (`{"offer": null}`), and the order has no `delivery_deliverytask` row (read-only SQL: order 372 had `task = NULL`). The worker log shows the dispatch task failing:
```
File ".../apps/delivery/services/dispatch.py", line 236, in dispatch_order
    _later(expire_offer, (offer.pk,), settings.OFFER_TIMEOUT_SECONDS)
File ".../apps/delivery/services/dispatch.py", line 69, in _later
    if settings.CELERY_TASK_ALWAYS_EAGER:
AttributeError: 'Settings' object has no attribute 'CELERY_TASK_ALWAYS_EAGER'.
```

## Root cause
`_later()` read `settings.CELERY_TASK_ALWAYS_EAGER`, which only `config/settings/test.py` defines. The backend's own tests run under test settings, so they passed.

## Resolution and verification
Fixed in `f5d39ff`: `getattr(settings, "CELERY_TASK_ALWAYS_EAGER", False)`, plus a regression test (`apps/delivery/tests/test_dispatch_settings.py`). QA restarted :8004 and the worker from `f5d39ff` under plain `config.settings.local`, with no QA overlay. `test_p5_tc34` and `test_p5_tc39` passed: the order got a task and an offer, and accept returned ASSIGNED (`2 passed in 80.82s`). Between `999ef38` and `f5d39ff`, QA kept going with a harness-only settings overlay (`qa/tools/settings_overlay/qa_settings_local.py`, never application code). That overlay is no longer used.
