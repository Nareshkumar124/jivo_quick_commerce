# BUG-0009: A signed webhook with an over-long payment id returns 500 instead of `ignored`

| Field | Value |
|---|---|
| Bug ID | BUG-0009 |
| Module | backend: `POST /api/v1/payments/razorpay/webhook/` (`apps/payments/services.py` `_dispatch`, `apps/orders/services.py` `capture_payment`, `apps/payments/refunds.py` refund key) |
| Owner agent | `django-backend-dev` |
| Severity | **P3 Minor** (brief scale: **Low**). Robustness only: it needs a correctly signed event, and genuine Razorpay payment ids are 18 characters. No money moves and nothing is stored (the transaction rolls back). |
| Priority | P3 |
| Status | Open |
| Found | 2026-11-04, QA Phase 3 stage 1 (P3-TC-57) |
| Environment | `qa/phase-2` at `c2c153a` (= `develop` merged in, Phase 3 R2b WIP), QA instance `127.0.0.1:8004` (local settings, FakeRazorpayGateway), shared remote PostgreSQL, Redis 6380 DB 5–7 |
| Test | `qa/tests/test_p3_payments.py::test_p3_tc57_webhook_overlong_ids` (`xfail(strict=True)`) |

## Steps to reproduce
1. As a QA customer, place an ONLINE order (`POST /api/v1/orders/`) and note `razorpay.order_id` and the bill's `grand_total`.
2. Send a `payment.captured` webhook for that gateway order, signed with the fake webhook secret (06 §2.6), whose `payload.payment.entity.id` is `"pay_" + 70 characters`, amount = `grand_total` in paise.
3. Send another one whose payment id is `"pay_" + 54 characters` (58 in total, within the 64-character column) with an amount 100 paise below `grand_total` (a wrong-amount capture, which the server refunds).

## Expected
06 §2.6, "Webhook results": a malformed payload is `ignored` ("stored with the error"), and 200 is returned. A 2xx tells Razorpay not to retry. 06 §6 reserves `SERVER_ERROR` for unexpected errors.

## Actual
```
step 2: HTTP 500 {"error":{"code":"SERVER_ERROR","message":"Something went wrong. Please try again.","details":{}}}
step 3: HTTP 500 (same body)
```
Instance log (`qa/private/logs/instance-local-p3.log`):
```
ERROR apps.core.exceptions Unhandled exception in RazorpayWebhookView
psycopg.errors.StringDataRightTruncation: value too long for type character varying(64)
django.db.utils.DataError: value too long for type character varying(64)
```
The order stays `PAYMENT_PENDING` (correct), and nothing is stored. Razorpay would retry the event for up to 24 hours, and each retry raises an ERROR log entry and a 5xx alert (09 §5).

## Possible root cause
- `Payment.gateway_payment_id` is `max_length=64` (`apps/payments/models.py`), but `_dispatch()` passes `entity["id"]` through unchecked. Only `KeyError`, `TypeError` and `ValueError` are mapped to `ignored`, not `DataError`.
- `Refund.idempotency_key` is also `max_length=64`, but the refund key is `f"capture:{payment_id}"` (8 + id). Any payment id longer than 56 characters overflows when a refund is needed (wrong amount, late capture or duplicate capture). That is why step 3 fails even though the payment id fits its own column.
- The verify endpoint is not affected: `RAZORPAY_PAYMENT_ID_PATTERN` bounds the id there.

## Suggested resolution
Validate the webhook entity ids (`id`, `order_id`) against the same patterns the verify serializer uses, and treat a mismatch as a malformed payload (`ignored`, stored with the error). Optionally, derive the refund key from a fixed-length hash of the payment id. Add a backend test for both cases.
