## Steps to reproduce (non-exploitable summary)
1. `POST /api/v1/auth/otp/request/` with `{"phone": "+91999990" + "०" + "098", "app": "customer"}`. The phone starts with an ASCII `+919`; the rest mixes Devanagari, full-width or Arabic-Indic digits.
2. `POST /api/v1/addresses/` with `"pincode": "1२२००१"` or `"receiver_phone"` containing non-ASCII digits.
3. `POST /api/v1/auth/otp/verify/` with `"otp": "１２３４５６"` (full-width).

## Expected
All three return `400 VALIDATION_ERROR`. 06 §2.1 says the phone is "an Indian mobile in E.164 (`+91[6-9]XXXXXXXXX`)". The published OpenAPI patterns (`^\+91[6-9]\d{9}$`, `^[1-9]\d{5}$`) are ASCII-only for the Dart and JS clients. 07 §2.1 says phones are E.164.

## Actual
- Step 1: `200 {"otp_length":6,"expires_in_seconds":300,"resend_after_seconds":30}`. An `OTPRequest` row is stored with the non-ASCII phone; 11 such rows were created by this QA run. Those spellings also get their own per-phone send counters.
- Step 2: `201 Created` with the non-ASCII PIN code or phone stored.
- Step 3: the code passes validation and costs a verify attempt: `400 OTP_INVALID {"attempts_remaining": 4}` instead of `VALIDATION_ERROR`.
- A value whose first digit is non-ASCII is rejected, because `[6-9]` and `[1-9]` are literal ASCII ranges. Only the `\d` parts accept Unicode digits.

## Evidence
```
'+919999900१98' 200
'+9199999०००98' 200
'+919٩٩٩٩٠٠٠٩8' 200
non-ascii OTP rows stored: ('+9199999०0098', 13), ('+919999900०98', 13), ...
verify unicode otp: 400 {"error":{"code":"OTP_INVALID","message":"The OTP is incorrect.","details":{"attempts_remaining":4}}}
```
SQL (read-only): `select count(*) from accounts_otprequest where phone !~ '^\+[0-9]+$'` returned 11.

## Possible root cause
`apps/accounts/validators.py` uses `RegexValidator(r"^\+91[6-9]\d{9}$")`, `r"^\d{6}$"` and `r"^[1-9]\d{5}$"`. With Python `str` patterns, `\d` matches any Unicode decimal digit (category Nd). `phone_validator` in `apps/accounts/models.py` has the same issue.

## Suggested resolution
Replace `\d` with `[0-9]`, or compile with `re.ASCII` (`RegexValidator(..., flags=re.ASCII)`), in all three validators and in the model's `phone_validator`. Add tests for Devanagari and full-width digits. Optionally, clean up the stored `OTPRequest` rows with non-ASCII phones; they expire through the 30-day purge anyway.

## Security impact (was private until the fix)

Per-phone OTP send limits (3 per 10 minutes, 10 per day; 09 §3.1) are keyed by the phone string exactly as sent. With non-ASCII digits accepted after the first digit, one real number has many spellings, and each spelling gets its own counter.

Reproduced on the QA instance (console SMS backend, no Celery worker consuming the QA broker DB, so nothing was sent):
```
ascii send 1 200 / 2 200 / 3 200 / 4 429 OTP_RATE_LIMITED   (+919999900098)
variant '+919999900०98' 200
variant '+91999990००98' 200
variant '+9199999०0098' 200
```
Impact depends on the SMS gateway (D-02, not chosen yet).
- If the gateway normalises Unicode digits to ASCII before delivery, an attacker can send far more OTP SMS to one victim than the per-phone limit allows (SMS pumping / harassment). Only the per-IP limit of 30 per hour per IP remains.
- With several source IPs (or `NUM_PROXIES` misconfigured), even that cap is weak.
- Unicode spellings would also create separate user accounts for one real number, if the victim's SMS arrives and is entered.

If the gateway rejects non-ASCII numbers, the impact is limited to junk rows and wasted attempts.

## Verification (QA run 2, 2026-11-03)
**Build:** `develop` at `0b801d1`, on QA instance `127.0.0.1:8004` (local settings, remote DB, then the local PostGIS fallback).

**Fix:**
- `apps/accounts/validators.py` uses `[0-9]` instead of `\d` in the phone, OTP and PIN code validators, matching the published patterns.
- The model `phone_validator` (migration `accounts.0005_ascii_phone_validator_anonymise_permission`) and the `app_version` validators (`cms.0002_ascii_version_validators`) are ASCII-only too.
- So is the store PIN code (`stores.0002_ascii_pincode_validator`).

**Evidence.** The strict xfail guards turned XPASS in the first run of QA run 2 (`qa/private/runs/run2-baseline-local.txt`, `run2-private-guards.txt`):
```
[XPASS(strict)] test_p1_tc04_otp_request_unicode_digits_rejected[+919999900\uff1099]   -> 400 VALIDATION_ERROR
[XPASS(strict)] test_p1_tc04_otp_request_unicode_digits_rejected[+919999900\u096798]   -> 400 VALIDATION_ERROR
[XPASS(strict)] test_p1_tc13_verify_validation[patch3]  (full-width OTP)          -> 400, no attempt consumed
[XPASS(strict)] test_p1_tc52_unicode_digits_in_address[patch0..2] (PIN, receiver phone) -> 400
[XPASS(strict)] test_p1_tc14b_unicode_spelling_does_not_bypass_phone_limit       -> variant 400 after the ASCII phone hit 429
```
- The markers are removed. The cases are now plain regression tests, and 14b is back in `qa/tests/test_p1_limits.py`, extended to three variants (Devanagari, full-width and Arabic-Indic).
- Phase 2: the notify-me `phone` refuses non-ASCII digits (P2-TC-17: `+91900000०104` and `+９１9000000104` both return 400).
- DB (read-only): 0 live addresses with a non-ASCII PIN code, and 0 notify-me rows with a non-E.164 phone.
- The 20 `OTPRequest` rows with non-ASCII phones from QA run 1 (before the fix) remain; the 30-day purge will remove them.

**Residual observation (OBS-09, not this bug):** `lat`/`lng` are numbers, parsed with `float()`, which accepts Unicode digits (`"२८.४७१"` → 28.471). The value is normalised to the same float before use or storage, so nothing non-ASCII is stored. P4 strictness only.
