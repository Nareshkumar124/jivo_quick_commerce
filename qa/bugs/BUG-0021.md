# BUG-0021: Rider pickup (T9) sends no `order.status` OUT_FOR_DELIVERY to the order socket or the ops feed

| Field | Value |
|---|---|
| Bug ID | BUG-0021 |
| Module | backend: delivery task flow (`apps/delivery/services/tasks.py` `_commit_pickup`), order events (`apps/orders/events.py`) |
| Owner agent | `django-backend-dev` |
| Severity | **P2 Major** (brief scale: **Medium**). A main status change of the live-tracking flow is never pushed. While its socket is up, the customer's order screen stays on "Packed", and the OTP panel (shown only when OUT_FOR_DELIVERY, 06 §4.1) stays hidden until the screen re-reads REST. The ops live board (`/ws/ops/live/`) also misses the change. Workarounds exist: the T9 push and SMS carry the OTP, `notification.new` arrives, and REST `track` is correct. No money, stock or security impact. |
| Priority | P1 (P6 live-tracking gate; small fix) |
| Status | Open |
| Found | 2026-11-10, QA stage 3 (P6, T-612 suite) |
| Environment | QA instance `127.0.0.1:8004` (`config.settings.local`, runserver/daphne, Redis 6380 DB 5/6/7), QA Celery worker (threads, 16) on DB 7, shared dev DB. Build: develop `efb3c3d` (QA worktree `b87eb5f`). Code unchanged on develop `3f6fc42`. |
| Test | `qa/tests/test_p6_t612.py::test_p6_tc59_polling_fallback_matches_socket` (P6-TC-59; also blocks the socket part of P6-TC-14) |

## Steps to reproduce
1. As QA customer A (+919000000101), place a COD order at QA-02. R1 (+919000000103) accepts the offer (task ASSIGNED).
2. Open `ws://127.0.0.1:8004/ws/v1/orders/<id>/` as A and send `{"type":"auth","token":"<A access>"}` → `auth.ok` plus the snapshot.
3. R1: `POST /api/v1/rider/tasks/<task>/arrived-store/`, the store packs the order, then `POST /api/v1/rider/tasks/<task>/pickup/ {"order_code": "<code>"}` → **200**.
4. Wait 10 s on A's socket.

## Expected
- 06 §4.2: `/ws/v1/orders/{order_id}/` carries `order.status` for the order's status changes. `/ws/ops/live/` carries `order.status` for the permitted stores.
- 08 §9 table, row "T9 OUT_FOR_DELIVERY": push (+SMS) with the OTP to the customer, and the **board**.
- 06 §4.1: "when `order.status` is OUT_FOR_DELIVERY, re-read `GET /orders/{id}/track/`" (the apps rely on that message to fetch the OTP).

`order.status {status: "OUT_FOR_DELIVERY"}` reaches A's socket and the QA-02 ops feed within the 3 s live target (09 §1).

## Actual
Nothing arrives on A's socket. The pickup itself is correct: REST `track` shows OUT_FOR_DELIVERY / PICKED_UP, and the push and SMS are sent. Test output (`qa/private/runs/s3-p6-t612-run3.txt`):
```
________________ test_p6_tc59_polling_fallback_matches_socket _________________
E   AssertionError: no OUT_FOR_DELIVERY on the socket
E   assert None
E    +  where None = wait('order.status', 10, status='OUT_FOR_DELIVERY')
```
The QA worker log (`qa/private/logs/p5-worker.log`, order 773, pickup `POST …/tasks/380/pickup/ 200` at 13:03:14.768 IST) shows every T9 side effect except the order event: `publish_order_eta`, `publish_notification_new`, `send_push` / `send_sms` for `order.out_for_delivery`, and a `broadcast_ws` (task.status). There is **no** `Order event order.out_for_delivery` and no `realtime.publish_order_event`. For the same order, every other transition logged both: `order.placed`, `order.accepted`, `order.packing`, `order.packed` (13:03:08–13:03:13), and later `order.delivery_failed` and `order.returned` (13:03:28).

## Possible root cause
`apps/delivery/services/tasks.py` `_commit_pickup` (line 231) calls `transition(order, OUT_FOR_DELIVERY, …)` and then, at line 257, only `hooks.notify_order(order, "order.out_for_delivery", …)` (push + inbox). It never calls `events.emit(...)`. The order-socket and ops-feed broadcast (`realtime.publish_order_event`) hangs on `orders.events` (see `orders.tasks.order_event`). T10 (`events.emit(events.DELIVERED, …)`, line 419) and T13 (`events.emit(events.DELIVERY_FAILED, …)`, line 528) do emit. `apps/orders/events.py` defines no T9 event; its comment says "Push/WebSocket for T9 … go through apps.delivery.hooks", but `hooks.notify_order` does not publish `order.status`.

## Suggested resolution
Add an `OUT_FOR_DELIVERY = "order.out_for_delivery"` event (or a generic status event) to `orders/events.py`, emit it in `_commit_pickup` after the transition, and make sure the order-event handler publishes `order.status` (and the ETA) without sending a second push, because `notify_order` is already deduplicated per (event, customer, order). Add a backend test asserting that T9 broadcasts `order.status` OUT_FOR_DELIVERY to the order group and the store's ops group. QA will re-run P6-TC-59 and P6-TC-14.
