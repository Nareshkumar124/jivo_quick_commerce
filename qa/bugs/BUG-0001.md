# BUG-0001: Request body over 2.5 MB returns 500 SERVER_ERROR instead of a 4xx

| Field | Value |
|---|---|
| Bug ID | BUG-0001 |
| Module | backend: `apps/core/exceptions.py` (error envelope), every JSON POST/PATCH endpoint |
| Owner agent | `django-backend-dev` |
| Severity | **P3 Minor** (brief scale: **Low**) |
| Priority | P2 |
| Status | **Verified** (QA run 2, 2026-11-03, commit `0b801d1`) |
| Found | 2026-11-02, QA run 1 |
| Environment | Commit `4960527`. QA instance `127.0.0.1:8004`, from a clean `git archive` export of the commit. Reproduced with both `config.settings.local` (DEBUG on) and `config.settings.staging` (DEBUG off). Shared remote PostgreSQL 16 and Redis 6380 DB 5–7. |
| Test | `qa/tests/test_p0_foundation.py::test_p0_tc08b_oversized_body_is_a_client_error` (xfail, strict) |

## Steps to reproduce
1. `POST /api/v1/auth/otp/verify/` with `Content-Type: application/json` and a body of about 3 MB, for example `{"phone": "+919999900099", "app": "customer", "pad": "<3,000,000 x characters>"}`.
2. The same happens on any JSON endpoint, authenticated or not, because the body is read during DRF parsing.

## Expected
The request is rejected as a client error: `400 VALIDATION_ERROR` or `413` in the error envelope. 06 §6 defines `SERVER_ERROR` as "Unexpected error", and 09 §5 alerts on the API 5xx rate, so oversized input should never count as one.

## Actual
```
HTTP 500
{"error":{"code":"SERVER_ERROR","message":"Something went wrong. Please try again.","details":{}}}
```
Server log (QA instance) at ERROR level:
```
ERROR apps.core.exceptions Unhandled exception in OtpVerifyView
  File ".../rest_framework/request.py", line 364, in _parse
    stream = io.BytesIO(self.body)
  File ".../django/http/request.py", line 425, in _check_data_too_big
django.core.exceptions.RequestDataTooBig: Request body exceeded settings.DATA_UPLOAD_MAX_MEMORY_SIZE.
ERROR django.request Internal Server Error: /api/v1/auth/otp/verify/
```

## Evidence
- The 500 response body above. The good part: it leaks no internals (P0-TC-09 passes).
- Log excerpt from `qa/private/logs/instance-local-*.log`.

## Possible root cause
`apps/core/exceptions.py`, `_normalise()` (around lines 117–125) maps `Http404`, `PermissionDenied` and `ValidationError` to DRF exceptions, but not `django.core.exceptions.SuspiciousOperation` subclasses such as `RequestDataTooBig`. Because DRF's handler returns `None` for them, they fall into the "unhandled" branch: logged as an error and answered with a 500.

## Suggested resolution
In `_normalise()`, map `RequestDataTooBig`, or `SuspiciousOperation` in general, to a 400 `VALIDATION_ERROR`, or to a 413 with a new additive code, and log it at WARNING. Add a backend test. In deployed environments, also set nginx `client_max_body_size` (02 §8) so oversized bodies are cut off before Django.

## Verification (QA run 2, 2026-11-03)
**Build:** `develop` at `0b801d1`, from a clean export, on QA instance `127.0.0.1:8004`. Local settings were used on the remote DB and on the local PostGIS fallback; staging settings (DEBUG off) were also used, see `03-api-testing-report.md`.

**Fix:** `apps/core/exceptions.py` `_normalise()` now maps `SuspiciousOperation` to client errors. `RequestDataTooBig` becomes 413 `PAYLOAD_TOO_LARGE`, and the other subclasses become 400 `VALIDATION_ERROR`. These are logged at WARNING on `django.security.*`. The code is in 06 §6 and `ErrorCodeEnum`.

**Black-box evidence** (`qa/tests/test_p0_foundation.py::test_p0_tc08b_oversized_body_is_a_client_error`; the xfail marker was removed):
```
POST /api/v1/auth/otp/verify/ (3 MB, anonymous)          -> 413 {"error":{"code":"PAYLOAD_TOO_LARGE",...,"details":{}}}
PATCH /api/v1/me/ (3 MB, customer JWT)                    -> 413 PAYLOAD_TOO_LARGE
POST /api/v1/serviceability/notify-me/ (3 MB, P2)         -> 413 PAYLOAD_TOO_LARGE
instance log: WARNING django.security.RequestDataTooBig Request body exceeded settings.DATA_UPLOAD_MAX_MEMORY_SIZE.
              WARNING django.channels.server HTTP POST /api/v1/auth/otp/verify/ 413 [0.01, ...]   (no ERROR, no traceback)
```
**Note (OBS-12):** 413 is documented once, globally, in the schema's `info.description` ("Any request whose body is larger than 2.5 MB gets 413 `PAYLOAD_TOO_LARGE`"), not per operation. That is acceptable under 06 §6 ("Any endpoint can return it"). Generated clients have no typed 413, so the apps should map it through the shared error-code handler.

P0-TC-09 (500 envelope hides internals) lost its only trigger with this fix. It now uses the `db-down` instance profile.
