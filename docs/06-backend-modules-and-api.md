Django project: `backend/`. Each business area is a Django app under `backend/apps/`.
The **OpenAPI schema** (`/api/schema/`, generated by drf-spectacular) is the source of truth for request/response shapes. This document lists endpoints and their purpose.

### 1.1 Service-layer rule
Business logic lives in **service modules** (`apps/<app>/services.py`), not in views or serializers. Example: `orders.services.place_order(...)`, `orders.services.transition(order, to_status, actor)`, `inventory.services.reserve(...)`, `delivery.services.dispatch(order)`. Views stay thin, and services are unit-tested directly. State transitions **only** happen through `orders.services.transition()`, which validates against the state machine in [08-order-lifecycle.md](08-order-lifecycle.md), writes `OrderStatusHistory` and emits events.

### 1.2 Domain events
Services emit internal events (e.g., `order_placed`, `order_status_changed`, `task_assigned`). Handlers, run with `transaction.on_commit` and dispatched to Celery, send notifications, push WebSocket messages and start dispatch. This keeps side effects out of the core transaction and retryable.

### 2.1 Auth & account [P1]
| Method | Path | Auth | Purpose |
|--------|------|------|---------|
| POST | `/api/v1/auth/otp/request/` | Public | Send OTP to `phone` for `app` (`customer`/`rider`). Rate-limited. |
| POST | `/api/v1/auth/otp/verify/` | Public | Verify OTP. Returns `access`, `refresh`, `user`, `is_new_user` (+ `rider_status` for the rider app). |
| POST | `/api/v1/auth/token/refresh/` | Public | Rotate the refresh token |
| POST | `/api/v1/auth/logout/` | Customer | Blacklist the refresh token, deactivate the device |
| GET / PATCH | `/api/v1/me/` | Customer | Read / update name, email, notification prefs |
| POST | `/api/v1/me/delete/` | Customer | Request account deletion (requires a fresh OTP) |
| POST | `/api/v1/me/devices/` | Customer | Register/update the FCM token, platform, app, version |
| GET | `/api/v1/config/app/` | Public | `min_supported_version`, `latest_version`, `maintenance`, support contacts, policy URLs, feature flags |

Contract details (published in `backend/openapi/schema.yaml`, Phase 1 R1; the schema has request/response examples for every case):
- **operationIds:** `auth_otp_request`, `auth_otp_verify`, `auth_token_refresh`, `auth_logout`, `me_retrieve`, `me_update` (PATCH), `me_delete_account`, `me_device_register`, `config_app`.
- **Enums:** `app` = `customer`/`rider` (same as `X-App-Name`), `platform` = `android`/`ios` (same as `X-Platform`), OTP `purpose` = `login`/`delete_account`, `rider_status` = `NONE`/`PENDING_KYC`/`ACTIVE`/`REJECTED`/`SUSPENDED` (07 §2.8 statuses plus `NONE` = no rider profile).
- **OTP request** `{phone, app, purpose?}`: `phone` is an Indian mobile in E.164 (`+91[6-9]XXXXXXXXX`). Response `{otp_length, expires_in_seconds, resend_after_seconds}`, identical whether or not the phone has an account. Rate limits answer 429 `OTP_RATE_LIMITED` with `details.retry_after_seconds` and `Retry-After` (never the generic `RATE_LIMITED`).
- **OTP verify** `{phone, otp, app, terms_version}`: the body `app` must match the OTP's app and is authoritative over `X-App-Name`. `terms_version` (from `config/app`) is stored on the user with the acceptance time whenever it changes (DPDP consent, added in Phase 1 R2). Response `{access, refresh, user, is_new_user, rider_status, deletion_cancelled}`. Logging in during the 30-day deletion grace period **restores** the account and returns `deletion_cancelled: true`; after anonymisation the phone signs up as a new user. `rider_status` is **always present** (`NONE` until Phase 5 adds rider profiles); the customer app ignores it. `is_new_user` = this verification created the account; show complete-profile when `is_new_user` or `!user.is_profile_complete`. Wrong code: 400 `OTP_INVALID` with `details.attempts_remaining`; expired, used or out of attempts (5): 400 `OTP_EXPIRED`; deactivated account: 403 `PERMISSION_DENIED`. A `delete_account` OTP never signs in.
- **Token refresh** `{refresh}` → `{access, refresh}`. The old refresh token is revoked on use, atomically: of several requests with the same token, even concurrent ones, exactly one succeeds and the others get 401 `TOKEN_INVALID` "Token is blacklisted" (BUG-0003, P2 R3). So refreshes must stay single-flight in the apps. Reuse detection (revoking the whole session family when a used token comes back) is deferred to P8 hardening (PM, 2026-11-03). Only 401 `TOKEN_INVALID` ends the session; this endpoint is exempt from 426/503.
- **Logout** `{refresh, fcm_token?}` → 204, idempotent (already revoked or foreign tokens are ignored).
- **Me**: `{id, phone, name, email, marketing_opt_in, is_profile_complete, rider_status, created_at}`. PATCH accepts `name` (not blankable), `email` (published as one nullable `string`/`email` since Phase 1 R3, without the `oneOf` the Dart generator could not handle; unique, null or "" clears; a conflict answers `VALIDATION_ERROR` with the generic "This email can't be used." so other accounts are not revealed), `marketing_opt_in`. `phone` is read-only in v1.
- **Account deletion** (fresh OTP): `POST /auth/otp/request/` with the caller's phone and `purpose: delete_account`, then `POST /me/delete/ {otp, reason?}`. Only a `delete_account` OTP issued to the caller's phone is accepted. Response `{deleted_at, anonymise_after}` (30-day grace, 07 §4); all refresh tokens are revoked, access tokens stop working and devices are deactivated. Staff accounts get 403 `PERMISSION_DENIED` (deleted by an administrator).
- **Devices**: `POST /me/devices/ {fcm_token, app, platform, app_version}` is an upsert keyed on `fcm_token` (moves to the caller if registered to someone else); always 200.
- **Config** `GET /config/app/`: versions and `store_url` are for the `X-App-Name` + `X-Platform` of the request (null without those headers), plus `maintenance`, `maintenance_message`, `support {phone, email}`, `policy_urls {terms, privacy, refund}`, `terms_version`, `otp {length, resend_after_seconds}`, `rider_location {active_interval_seconds, idle_interval_seconds}` (04 §3) and `feature_flags` (name → bool; ignore unknown keys).
- **Redis outage (09 §2):** `config/app` and the 426/503 guard fall back to the database when the cache is down. OTP rate limiting is **fail-closed**: `otp/request`, `otp/verify` and `me/delete` answer 503 `SERVICE_UNAVAILABLE` ("Sign-in is temporarily unavailable…") instead of sending or checking OTPs without counters. Fixed-OTP test numbers skip the counters and keep working.
- **426 / 503 on app endpoints:** every `/api/v1/` endpoint except `config/app` and `auth/token/refresh` can answer 426 `APP_UPDATE_REQUIRED` (`details: {min_supported_version, latest_version, store_url}`) and 503 `MAINTENANCE`. 426 is sent only when `X-App-Name`, `X-Platform` and `X-App-Version` are all present and the version is below the minimum; requests without them never get 426.

### 2.2 Addresses [P1]
| Method | Path | Auth | Purpose |
|--------|------|------|---------|
| GET / POST | `/api/v1/addresses/` | Customer | List / create (includes `lat`, `lng`) |
| GET / PATCH / DELETE | `/api/v1/addresses/{id}/` | Owner | Read / update / delete (soft) |
| POST | `/api/v1/addresses/{id}/set-default/` | Owner | Make default |

Contract details: operationIds `addresses_list`, `addresses_create`, `addresses_retrieve`, `addresses_update` (PATCH; no PUT), `addresses_delete`, `addresses_set_default`. The list is paginated per 02 §5 (default first, then newest). `label` = `home`/`work`/`other` plus optional `custom_label`. `lat`/`lng` are JSON numbers and **required** (03 §2.4: the map pin is required). `receiver_name`/`receiver_phone` default to the user's own; sending `""` for either resets it to the user's own name/phone (T-205, Phase 2: the generated client drops nulls, so an empty string is the reset signal). `null` is rejected with 400 `VALIDATION_ERROR`, and omitting the field leaves it unchanged. Phone, OTP and PIN code fields accept ASCII digits only (BUG-0002): `+91९…` or `１２２００１` is a 400. An invalid `page` (0, past the end, not a number) answers 404 `NOT_FOUND` "Invalid page." on every paginated list, and the schema documents it (BUG-0004). `is_default` is read-only: the first address becomes the default, `set-default` moves it, and deleting the default promotes the most recently updated remaining address. Another user's address id answers 404 `NOT_FOUND`.

### 2.3 Serviceability & stores [P2]
| Method | Path | Auth | Purpose |
|--------|------|------|---------|
| GET | `/api/v1/serviceability/?lat=&lng=` | Public | `{serviceable, store: {id, name, is_open, opens_at}, eta_minutes, message}` |
| POST | `/api/v1/serviceability/notify-me/` | Public/Customer | Save interest for an unserviced location |

Contract details (published in `backend/openapi/schema.yaml`, Phase 2 R1; examples for every case):
- **operationIds:** `serviceability_check`, `serviceability_notify_me` (tag `serviceability`).
- **Check** `GET /serviceability/?lat=&lng=` (public, credentials ignored): a valid point **always answers 200** `{serviceable, store, eta_minutes, message}`. `store` = `StoreStatus {id, name, is_open, opens_at}`, null when not serviceable. `is_open` = inside opening hours **and** accepting orders; a closed store is still `serviceable: true` (browse allowed, checkout disabled). `opens_at` = UTC datetime of the next opening, null when open or when paused (`is_accepting_orders=false`) with no known reopening. `eta_minutes` (08 §8) is null unless serviceable and open; `message` (display text, IST times) is null when serviceable and open. Overlapping areas: nearest open store (07 §2.2). This endpoint never returns `NOT_SERVICEABLE` / `STORE_CLOSED`; those 422 codes belong to the actions that need an open store (cart address and order placement, Phase 3). Missing or out-of-range `lat`/`lng`: 400 `VALIDATION_ERROR`.
- **Notify-me** `POST /serviceability/notify-me/ {lat, lng, phone?, address_text?}` → 201 `{id, lat, lng, phone, address_text, created_at}`. Optional authentication: a sent token is checked (401 `TOKEN_INVALID` if invalid) and links the request to the user, whose phone is the default. Anonymous requests without a phone are kept as a demand signal. Rate-limited (429 `RATE_LIMITED`).
- **Addresses** (06 §2.2) gain a read-only `is_serviceable` (bool, computed on read; unserviceable addresses can be saved but not ordered to, 03 §2.4). Additive.
- **Implementation (Phase 2 R2):** `DarkStore.service_area` is a PostGIS MultiPolygon (SRID 4326, GiST). The check itself runs on a snapshot of the active stores (area, location, hours) cached in Redis and invalidated on any store or timing change; point-in-polygon runs in-process with GEOS (the engine PostGIS uses), so the hot path does no database query (p95 16-20 ms measured on the dev server against the remote DB, where a new DB connection alone costs about 110-290 ms). A cache miss or Redis outage loads the snapshot from PostGIS. Candidates are ranked open first, then nearest (great-circle distance to `location`), then lowest `priority`. ETA = `avg_prep_minutes` + `ETA_RIDER_WAIT_MINUTES` (3) + straight-line km × `ETA_ROAD_FACTOR` (1.3) / `ETA_AVG_SPEED_KMPH` (20) × 60 + `ETA_BUFFER_MINUTES` (2), rounded up. Opening hours are `StoreTiming` windows in IST. Notify-me merges a signed-in user's repeat within 24 h and 100 m into their own lead. An anonymous request is **never merged**: it always gets a lead of its own, so its response (`id`, `created_at`, the values it sent) can never reveal an earlier submission (BUG-0008, Phase 3 R2b and its review: a typed phone proves nothing, and returning an identical submission's `id` would confirm that someone sent that phone and address). Anonymous repeats are bounded by the throttle; expansion reports count distinct phones. Notify-me is throttled with `NOTIFY_ME_RATE` (default 10/hour per user or IP; fails open when Redis is down). `Address.is_serviceable` is one `EXISTS` subquery per list.

| Method | Path | Auth | Purpose |
|--------|------|------|---------|

| GET | `/api/v1/categories/` | Public | Category tree |
| GET | `/api/v1/products/?category=&collection=&sort=&page=` | Public | Product list with variants, price and store availability |
| GET | `/api/v1/products/{id_or_slug}/` | Public | Product detail with all variants, images, attributes, similar products |
| GET | `/api/v1/search/?q=` | Public | Search results (paginated) |
| GET | `/api/v1/search/suggest/?q=` | Public | Typeahead suggestions |
| GET | `/api/v1/collections/{slug}/` | Public | Collection with products |

Contract details (published in `backend/openapi/schema.yaml`, Phase 2 R1; examples for every case, with consistent money):
- **operationIds** (tag `catalog`): `home_retrieve`, `categories_list`, `products_list`, `products_retrieve`, `search_products`, `search_suggest`, `collections_retrieve`.
- **`X-Store-Id`** (integer, required on all seven; the store id from serviceability): missing/blank → 400 `VALIDATION_ERROR` `details: {"X-Store-Id": ["This header is required."]}`; not a positive integer → 400 `VALIDATION_ERROR` `{"X-Store-Id": ["A valid store id is required."]}`; unknown or deactivated store → **404 `STORE_NOT_FOUND`** (`details: {store_id}`; the app drops its saved store and re-checks serviceability). A closed store is browsable (no `STORE_CLOSED` on catalog reads).
- **Authentication:** all public. `home_retrieve` is *optionally* authenticated (a sent token is checked: 401 `TOKEN_INVALID` when invalid, never silently anonymous) to fill `buy_again`; the others ignore credentials.
- **Product tile** `ProductCard {id, slug, name, brand, is_veg, image, default_variant_id, variants[]}`. `default_variant_id` is the variant the tile shows and ADD adds (the collection item or past purchase in that context, else the first in stock, else the first). `variants` = every active variant the store sells (out-of-stock included), never empty; products the store does not sell are never listed. `VariantSummary {id, name, mrp, selling_price, discount_amount, discount_percent, unit_price, stock_status, orderable_quantity, units_left, max_qty_per_order, image}`: money as 2-decimal strings (store price override applied), `discount_percent` rounded **down**, `unit_price {amount, per}` nullable. Stock: `stock_status` = `IN_STOCK`/`LOW_STOCK`/`OUT_OF_STOCK`; `orderable_quantity` = min(available at the store, `max_qty_per_order`), the stepper cap (0 = out of stock); `units_left` only when `LOW_STOCK` ("Only 2 left"), so exact stock is never published. The low-stock display threshold is a server setting (proposed default 3, D-09 values), separate from the store's re-order `low_stock_threshold`.
- **Images** `ImageSet {thumbnail, medium, large, alt_text}` (about 256/512/1024 px wide, made at upload). Component names avoid Flutter class names (`Image`, `Banner`, `Category`).
- **Home** `HomeFeed {store: StoreStatus, banners[], categories[], collections[], buy_again[]}`. Banners: `link_type` = `category`/`collection`/`product` (`link_value` = slug), `url` (absolute https), `none`. Collection rails: up to 10 products, out-of-stock last, `has_more`. `buy_again`: up to 10 variants from delivered orders sold at the store, empty when anonymous.
- **Categories** `{results: [CategoryNode {id, name, slug, image, children: [CategoryTile]}]}`: two levels, only categories with products at the store, not paginated.
- **Products** `?category=&collection=&sort=&page=&page_size=`: `category`/`collection` take an id or slug (a top-level category includes its sub-categories); unknown → 404 `NOT_FOUND`. `sort` = `relevance` (default; admin/collection order) / `price_asc` / `price_desc` / `discount`, prices of the default variant; in-stock first for every sort. Standard page (02 §5).
- **Product detail** `/products/{id_or_slug}/`: `ProductDetail` = tile fields plus `category`, `short_description`, `description` (plain text), `highlights[]`, `variants[]` (`VariantDetail` adds `sku`, `net_quantity`, `images[]` = the gallery when selected), `ingredients`, `nutrition` (`{columns[], rows[{name, values[], is_sub_row}]}` or null), `shelf_life`, `storage_instructions`, `country_of_origin`, `manufacturer`, `marketer`, `importer`, `consumer_care`, `fssai_license_no` (label strings "" when not applicable; 09 §4), `similar_products[]` (up to 10). 404 `NOT_FOUND` when unknown, inactive or not sold at the store.
- **Search** `/search/?q=&sort=&page=&page_size=`: `q` required (1–100 chars, trimmed); same tiles and sorts; no results = 200 with `count: 0`. **Suggest** `/search/suggest/?q=`: `{query, suggestions: [{type: product|category|keyword, text, query, id, slug, image}]}`, up to 10; blank or missing `q` returns the **trending searches** (03 §2.7) as `keyword` items.
- **Collection** `/collections/{slug}/` → `{id, name, slug, products[]}`: up to 100 products in collection order, out-of-stock last; for sorting/paging use `/products/?collection=`.
- **Implementation (Phase 2 R2):** bodies are cached per store in Redis (`CATALOG_CACHE_SECONDS`, 300 s), keyed by a global catalog version and a per-store version that are bumped after commit by any catalog change or stock row change (so a banner's start/end time can lag by up to 300 s). Store status and `buy_again` are never cached (status is computed from the cached store hours on each request). `X-Store-Id` is resolved from the same cached store snapshot as serviceability, so a warm catalog request does no database query (p95 14-26 ms measured on the dev server; a cold build is 175-480 ms against the remote DB). If Redis is down, responses come from the database. `buy_again` stays `[]` until orders exist (Phase 3/4). Images are public media with fixed renditions (256/512/1024 px WebP, EXIF stripped, random keys).

### 2.5 Cart & coupons [P3]
| Method | Path | Auth | Purpose |
|--------|------|------|---------|
| GET | `/api/v1/cart/?address_id=` | Customer | Cart with items, stock flags and full **bill** (computed by the pricing engine) |
| POST | `/api/v1/cart/items/` | Customer | Add `{variant_id, quantity}` (validates stock and max qty) |
| PATCH / DELETE | `/api/v1/cart/items/{id}/` | Owner | Change qty / remove |
| DELETE | `/api/v1/cart/` | Customer | Clear cart |
| GET | `/api/v1/cart/coupons/` | Customer | Coupons with eligibility and savings for the current cart |
| POST / DELETE | `/api/v1/cart/coupon/` | Customer | Apply `{code}` / remove the coupon |
| PATCH | `/api/v1/cart/` | Customer | Set `tip`, `instructions`, `address_id` |

Contract details (published in `backend/openapi/schema.yaml`, Phase 3 R1; examples for every case, with money recomputed from 08 §6.2 by `apps/cart/tests/test_contract.py`):
- **operationIds** (tag `cart`): `cart_retrieve`, `cart_update` (PATCH), `cart_clear` (DELETE `/cart/`), `cart_items_add`, `cart_items_update` (PATCH), `cart_items_delete`, `cart_coupons_list`, `cart_coupon_apply`, `cart_coupon_remove`. All need a customer token and take **`X-Store-Id`** with the same rules as the catalog (400 missing/malformed, 404 `STORE_NOT_FOUND`).
- **The cart follows `X-Store-Id`:** one cart per user; on every call its lines keep their quantities and take that store's prices and stock. The cart never reserves stock (08 §6.1).
- **Every call returns the whole `Cart`** (200), so the app never computes money: `store` (`StoreStatus`), `items[]` (`CartLine {id, product {id, slug, name, brand, is_veg}, variant: VariantSummary, quantity, line_mrp_total, line_total, issue}`), `item_count` (units), `coupon` (`{code, title, discount, is_applicable, message, amount_to_unlock}` or null; `amount_to_unlock` added in Phase 3 R2b for the customer app: the item value still needed when the coupon stopped applying because of its minimum, else null), `tip`, `instructions {chips[], note}` (chips `DONT_RING_BELL`/`LEAVE_AT_DOOR`/`AVOID_CALLING`, each once; note ≤ 200), `address` (the `Address` component or null), `bill`, `thresholds`, `payment_methods[]`, `checkout`.
- **`Bill`** = exactly the 08 §6.2 amounts `{mrp_total, item_total, product_discount, coupon_discount, delivery_fee, small_cart_fee, handling_fee, tip, grand_total}` plus `total_savings` (= product + coupon discount), all 2-decimal strings. The same component is the order's bill. An empty cart's bill is all zeros.
- **`thresholds`** `{min_order_value, amount_to_min_order, free_delivery_threshold, amount_to_free_delivery}`: the amounts still needed (null when reached, or when the store charges no delivery fee), compared against `item_total` before the coupon (D-09), for the "Add ₹X more" nudges.
- **Line issues:** a line whose quantity is above `variant.orderable_quantity` has `issue {code: OUT_OF_STOCK | QUANTITY_UNAVAILABLE, message}`; the fix is to set it to `orderable_quantity` (remove at 0). The bill still shows the line as it is, and checkout is blocked until it is fixed (03 §2.8 "flagged with a fix action"; the server never changes the cart silently).
- **`checkout {can_place_order, blockers[{code, message}]}`**: `CheckoutBlockerCodeEnum` = `CART_EMPTY` (an empty cart has only this one), `ADDRESS_REQUIRED`, `NOT_SERVICEABLE`, `STORE_CLOSED`, `STOCK_UNAVAILABLE`, `MIN_ORDER_NOT_MET`, `COUPON_INVALID`/`COUPON_EXPIRED`/`COUPON_NOT_ELIGIBLE`/`COUPON_USAGE_EXCEEDED`. Values that are also error codes are the error `POST /orders/` would return.
- **`payment_methods`**: `[{method: ONLINE|COD, is_available, unavailable_reason: COD_DISABLED|ABOVE_LIMIT|NOT_ALLOWED|null, message}]`, ONLINE then COD. COD is shown only when available (03 §2.9).
- **`GET /cart/?address_id=`** checks the cart against another saved address without saving it (unknown or another user's address: 400 `VALIDATION_ERROR`). The address is otherwise the one saved with `PATCH /cart/` (null until set).
- **`POST /cart/items/ {variant_id, quantity}` sets the line's quantity** (it does not add to it), so a retried request never doubles a line; `quantity: 0` removes it. An increase is checked: above `max_qty_per_order` → 422 `MAX_QTY_EXCEEDED` `{variant_id, max_qty_per_order}`; above stock → 409 `STOCK_UNAVAILABLE` `{items: [{variant_id, requested_quantity, orderable_quantity}]}` (a variant the store does not sell has `orderable_quantity` 0). A decrease is always accepted. `PATCH /cart/items/{id}/ {quantity ≥ 1}` has the same rules; `DELETE` removes. Another user's line id is 404.
- **`PATCH /cart/` `{tip?, instructions?, address_id?}`**: tip 0 to `CART_MAX_TIP` (setting, default ₹500; also enforced by `compute_bill()`, code review F1); `instructions` replaces chips and note together; `address_id` outside the store's area → 422 `NOT_SERVICEABLE` `{address_id}` and nothing is saved. `DELETE /cart/` removes the lines, the coupon and the tip, and keeps the address and instructions.
- **Coupons:** `GET /cart/coupons/` → `{results: [CouponOffer {code, title, description, discount_type: FLAT|PERCENT, value, max_discount, min_order_value, ends_at, is_applied, is_eligible, savings, ineligible_reason, message, amount_to_unlock}]}`: visible coupons valid at the store now, eligible first by savings; not paginated. `POST /cart/coupon/ {code}` (case-insensitive) replaces any applied coupon; errors 422 `COUPON_INVALID` (unknown, inactive, not started), `COUPON_EXPIRED`, `COUPON_NOT_ELIGIBLE` (`details.reason` = `MIN_ORDER_VALUE` with `min_order_value` and `amount_to_unlock`, `FIRST_ORDER_ONLY`, `NO_ELIGIBLE_ITEMS` or `STORE`), `COUPON_USAGE_EXCEEDED` (`details.scope` = `per_user`/`total`). A coupon that stops applying (items removed) stays on the cart with `is_applicable: false`, discount 0 and a checkout blocker. `DELETE /cart/coupon/` is idempotent.
- **Implementation (Phase 3 R2a, live):** `apps.cart.services` (views are thin). `compute_bill()` is the only money function (cart now; order placement and T8a later). A store with no `PricingConfig` row is billed with the model defaults, which are the D-09 values since Phase 3 (min ₹99; delivery ₹25, free from ₹299; small-cart ₹15 below ₹149; handling ₹0; COD up to ₹2,000; PM default, migration `stores.0004` fills only rows still all zero). A cart's line prices and stock come from one annotated query (a variant the store does not sell, or that is no longer visible, has `orderable_quantity` 0); `GET /cart/` runs a fixed number of queries whatever the number of lines (test-asserted). Checkout blockers are listed in this order: `STORE_CLOSED`, `STOCK_UNAVAILABLE`, `MIN_ORDER_NOT_MET`, coupon, address. A soft-deleted address on the cart counts as none.
- **Coupon rules (Phase 3 R2a, `apps.promotions.services`)**, first failure wins: inactive or not started → `COUPON_INVALID`; expired → `COUPON_EXPIRED`; not offered at the store → `STORE`; used up (HELD + APPLIED redemptions count; per customer, default limit 1, and in total) → `COUPON_USAGE_EXCEEDED`; first-order coupon and the customer has an earlier order that **reached PLACED** (a failed or abandoned online payment does not count) → `FIRST_ORDER_ONLY`; `item_total` (before the coupon) below `min_order_value` → `MIN_ORDER_VALUE`; category coupon without a qualifying item (a top-level category includes its sub-categories) → `NO_ELIGIBLE_ITEMS`. Discount: FLAT = value; PERCENT = value % of the eligible subtotal, half-up to the paisa; capped by `max_discount` and by the **eligible subtotal** (so a category coupon never gives more than its items cost; PM decision). The coupon sheet leaves out coupons the customer (or everyone) has used up.

- **`POST /orders/`** takes `Idempotency-Key` **and `X-Store-Id`** (the store the cart is priced at; added in Phase 3) and `{address_id, payment_method: ONLINE|COD, expected_grand_total}`. `expected_grand_total` (added in Phase 3) is the cart's `bill.grand_total` as displayed: the 08 T1 guard "bill matches the client's displayed total"; a mismatch is 409 `PRICE_CHANGED` `{expected_grand_total, grand_total}`. Other errors: 400 (headers, body, `{"non_field_errors": ["Your cart is empty."]}`, unknown address), 409 `STOCK_UNAVAILABLE` `{items: [{variant_id, requested_quantity, orderable_quantity}]}` (any line above its `orderable_quantity`, whether from stock or the per-order limit), 422 `NOT_SERVICEABLE` `{address_id}`, `STORE_CLOSED` `{store_id, opens_at}`, `MIN_ORDER_NOT_MET` `{min_order_value, item_total, amount_to_min_order}`, `COD_NOT_AVAILABLE` `{reason, cod_max_order_value?}`, the coupon codes, 409 `INVALID_STATE_TRANSITION` `{pending_order_id}` when another of the customer's orders is still PAYMENT_PENDING (PM decision: one unpaid order at a time, so stock is never held twice; the app offers retry or cancel), and 503 `SERVICE_UNAVAILABLE` when the payment gateway is unreachable (nothing created). Response **201** `OrderPlacement {order: Order, razorpay: RazorpayCheckout | null}`; COD orders are PLACED with `razorpay: null`. A repeat with the same key answers **200** with the first order in its current state (`razorpay` only while it awaits payment); the same key with a different body is 400 `{"Idempotency-Key": [...]}`; only a successful placement is remembered.
- **`Idempotency-Key`** (02 §5): required on `orders_create` and `orders_retry_payment`, 8–64 of `[A-Za-z0-9_-]` (a UUID is recommended), per user. Verify needs none: it is idempotent by itself.
- **Rate limits** (code review of R1): `orders_create` is limited per user (`ORDERS_CREATE_RATE`, default 30/hour); `orders_retry_payment` and `payments_razorpay_verify` share `PAYMENTS_RATE` (default 60/hour). Over the limit: 429 `RATE_LIMITED` with `details.retry_after_seconds` and `Retry-After`. They fail open when Redis is down (a lost limit is better than a lost order; OTP limits fail closed instead, DL-13).
- **`Order`** `{id, order_number, status (OrderStatusEnum, all 11 states of 08 §1), payment_method, payment_status (07 §2.6), store {id, name}, items[OrderLine {id, variant_id, product_id, product_name, variant_name, image, mrp, selling_price, quantity, line_mrp_total, line_total}], item_count, bill: Bill, coupon_code, address (snapshot, the Address fields without id/flags), instructions, created_at, placed_at, payment_expires_at, eta_at, can_cancel, can_retry_payment}`. `payment_expires_at` is set only while PAYMENT_PENDING (placement + the 15-minute window; a retry does not extend it). `eta_at` is set from PLACED. P4 adds the timeline and invoice fields (additive).
- **`RazorpayCheckout`** `{key_id, order_id, amount (integer paise = grand_total × 100), currency "INR", name, description, prefill {name, contact, email}, expires_at, timeout_seconds}`: the options for Razorpay checkout, passed through unchanged.
- **`GET /orders/?status=active|past`** → paginated `OrderSummary {id, order_number, status, payment_method, payment_status, store, item_count, images (≤ 4), grand_total, created_at, placed_at, payment_expires_at, eta_at, can_retry_payment}`. `active` = every non-terminal state, PAYMENT_PENDING included (recovering a payment after the app was closed, 03 §2.9); without `status`, active orders come first.
- **`POST /orders/{id}/retry-payment/`** (`Idempotency-Key`) → 200 `OrderPlacement` with a new Razorpay order; 409 `INVALID_STATE_TRANSITION` `{status}` when the order is not awaiting payment or the window has ended.
- **`POST /orders/{id}/cancel/ {reason, note?}`**: reasons `CHANGE_PAYMENT_METHOD`, `PAYMENT_PROBLEM`, `ORDERED_BY_MISTAKE`, `CHANGED_MIND`, `DELIVERY_TOO_SLOW`, `OTHER`; 200 `Order`. Added to Phase 3 for T5 (the customer gives up on paying or wants to pay another way: stock and coupon hold released, cart kept), so in Phase 3 only PAYMENT_PENDING is cancellable; Phase 4 widens it to 08 §7. Otherwise 409 `INVALID_STATE_TRANSITION` `{status}`.
- **`POST /payments/razorpay/verify/ {order_id, razorpay_order_id, razorpay_payment_id, razorpay_signature}`** → 200 `Order` (PLACED). 400 `PAYMENT_VERIFICATION_FAILED` (signature, or a Razorpay order that is not this order's); 404 for another user's order; 409 `INVALID_STATE_TRANSITION` when the order already failed or was cancelled (never revived; a captured payment is auto-refunded, T3a). Idempotent: repeats, or a verify after the webhook, return the PLACED order.
- **`POST /payments/razorpay/webhook/`**: no JWT; `X-Razorpay-Signature` = hex HMAC-SHA256 of the **raw body bytes** with the webhook secret (else 400 `PAYMENT_VERIFICATION_FAILED`, nothing stored), `X-Razorpay-Event-Id` required (the idempotency key, Razorpay's header). 200 `{status: processed|duplicate|ignored}`. Exempt from the 426/503 app guards, so maintenance never refuses a payment event.
- **Gateway** (DL-21): `apps.payments.gateways.PaymentGateway` (`create_order`, `fetch_order_payments`, `refund`, signature checks), selected by `PAYMENT_GATEWAY`. `RazorpayGateway` reads `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET` and `RAZORPAY_WEBHOOK_SECRET` from the environment only and fails loudly without them. `FakeRazorpayGateway` is the local and test default; staging and production refuse it with the system check `payments.E001` and in its constructor (no opt-in).
- **Fake payment gateway (local development only):** lets a `dev` build pay without Razorpay keys.
  1. `POST /orders/` (ONLINE) returns `razorpay.key_id = "rzp_fake_jivo_local"` and `razorpay.order_id = "order_" + 14 letters/digits`. That key id means: do not open Razorpay checkout.
  2. Make up a payment id `"pay_" + 14 letters/digits` (e.g. random).
  3. Signature = lowercase hex HMAC-SHA256 of the UTF-8 string `"<order_id>|<payment_id>"`, keyed with the published dev-only secret `jivo-fake-razorpay-key-secret-local-only`. This is Razorpay's own algorithm, so verify runs the same code as in production. Worked example (the schema's verify example): `order_Nq3uVxY7kL9pQe|pay_Nq3vA1bC2dE3fG` → `bc4bcc84a495aaddc2f52819146edd4d26728c1221e5621f23995c106721c977`.
  4. Call `POST /payments/razorpay/verify/` with them. To simulate a failure, skip verify (or send a wrong signature: 400 `PAYMENT_VERIFICATION_FAILED`) and use retry or cancel.
  - A signed webhook can be simulated the same way: `X-Razorpay-Signature` = hex HMAC-SHA256 of the exact body bytes with `jivo-fake-razorpay-webhook-secret-local-only`.
  - These values are not secrets: they work only with the fake gateway, which deployed environments refuse.
- **Implementation (Phase 3 R2b, live):** `apps.orders.services` (placement, `transition()`, capture, cancel, expiry, retry) and `apps.payments.services` (verify, webhook); views are thin and every order lookup is scoped to the caller (another user's id is 404). No operation answers 503 "not available yet" any more.
  - **Order number** `JV-YYMMDD-NNNNNN`: the IST date and the order's own id (allocated first from the table's sequence), so it is unique without another table.
  - **Placement** checks, in order: replay of the key; another order of the customer in PAYMENT_PENDING (409 `pending_order_id`); the address (400 unknown, 422 `NOT_SERVICEABLE`); the store open (422 `STORE_CLOSED`); the cart (400 empty, 409 `STOCK_UNAVAILABLE`, 422 `MIN_ORDER_NOT_MET`, the coupon, 409 `PRICE_CHANGED`, 422 `COD_NOT_AVAILABLE`); then the gateway order (503 if down); then, in one transaction, the order, its items, the payment attempt, the coupon use and the stock reservation. A race lost on the coupon's last use (422) or the last unit (409) rolls everything back.
  - **Lock order** (one for every path, so nothing deadlocks): the `Order` row, the customer's `Cart` row, the `Coupon` row, then `StoreInventory` rows in variant-id order. Placement takes cart, coupon, stock; capture takes order, cart; cancel and expiry take order, stock.
  - **Capture** (`capture_payment`, whichever of verify, the `payment.captured` webhook or the expiry job reports it first; repeats are no-ops): PAYMENT_PENDING → PLACED (T3, `payment_status` PAID, ETA set, the reservation stops expiring, the held coupon becomes used, the **ordered lines and the coupon leave the cart**, anything added since stays). A capture whose amount is not the order's `grand_total` never places the order (it keeps waiting for a correct payment until its window ends): the attempt is recorded as a CAPTURED `Payment` with the amount actually captured and refunded in full (a `Refund` with reason `amount_mismatch`, key `capture:<payment id>`), and the ops alert `payment.late_capture` is raised (OBS-P3-01). That refund does not change the order: its `payment_status` and `amount_refunded` (0) are untouched, because nothing was paid against the order itself. On a failed or cancelled order (T3a) the capture is refunded in full and the order shows `REFUND_PENDING`, then `REFUNDED` with `amount_refunded`; a second capture on an order already paid (e.g. after a retry) is refunded too, without touching the order (DL-45). Refunds: one `Refund` per capture (`idempotency_key`). The `payments.process_refund` task (code review M1 and its fix review) locks the order and the refund and re-checks that the refund is still PENDING without a gateway id. **Its guard is a lookup:** before every POST (not only on Celery retries, since a task redelivered after a worker crash starts at retry 0) it lists the payment's refunds (`GET /payments/{id}/refunds`) and adopts one whose `receipt` is this refund's key (`refund_receipt()`). Only if none matches does it POST the refund with that `receipt`. Timeouts and 5xx on either call are retried with backoff and nothing is recorded. Razorpay's docs say a repeated refund receipt is refused ("Duplicate receipt"); this is assumed (confirm in Razorpay test mode) and handled only as a fallback that looks the refunds up again. On "fully refunded already", a gateway refund of the same amount is adopted only when the payment has no other `Refund` row (otherwise it fails for ops, with a warning). Other 4xx are not retried: the refund is FAILED and the ops alert `payment.refund_failed` is raised once, on the change to FAILED (logged at ERROR in Phase 3). A FAILED refund never goes back to PENDING (a later `processed` still settles it). `payments.refunds.retry_failed_refund()` is the manual-retry hook for the Phase 4 ops screen: a new refund keyed `<original key>:retry-N`, numbered from the original key. `refund.processed`/`refund.failed` webhooks settle refunds too. An event whose refund id is not stored yet (`process_refund` still in its gateway call) is matched by `payment_id` + `receipt` and records the id. If nothing matches while a refund of that payment is PENDING without a gateway id and younger than `REFUND_WEBHOOK_RETRY_WINDOW_SECONDS` (default 7200 s: a little over `process_refund`'s longest life, about 95 min = 5490 s of backoff + 9 attempts × 2 calls × the 10 s timeout), the webhook answers **503** `SERVICE_UNAVAILABLE` and stores nothing, so Razorpay retries it. Past that window (a Dashboard refund without a receipt, a task that gave up) the event is logged at WARNING and answered `ignored`, so the 503 is bounded; an event for another payment is never a 503. The refund lookup asks for `count=100` (Razorpay pages 10 by default). The gateway call still runs under the order and refund row locks; moving it out is Phase 4 T-403c.
  - **Webhook results:** `processed`, `duplicate` (same `X-Razorpay-Event-Id` already processed) or `ignored` (an event type not handled, an unknown gateway order, a malformed payload: stored with the error). A payment or order id that is not a Razorpay id (the verify endpoint's patterns: `pay_`/`order_` + 10-40 letters and digits, so it always fits the stored fields and the refund key) is malformed, never a 500 (BUG-0009). The one non-2xx answer to a signed event is 503 for a `refund.*` event that cannot be matched yet (see Capture above), so the gateway retries it. An event is stored and processed in one transaction, so a failure leaves nothing and the gateway's retry processes it again. `payment.failed` only marks that attempt FAILED, under the order lock and only while it is still CREATED, so it never overwrites a capture (code review Minor 4): the customer may retry until the window ends.
  - **Auto-capture (PM decision, code review Minor 5):** every Razorpay order is created with the Orders API's per-order capture settings `payment: {capture: "automatic", capture_options: {automatic_expiry_period: 12, manual_expiry_period: 12, refund_speed: "normal"}}` (they override the Dashboard's; 12 minutes is the documented minimum and fits the 15-minute window; a payment authorised but not captured in time is refunded by Razorpay). Verify therefore treats a valid signature as a capture of the full amount (the gateway order is created for exactly `grand_total`); the webhook still checks the captured amount.
  - **Retry-payment** is refused (409) for an order that is not ONLINE and PAYMENT_PENDING (`This order is already paid.` when paid), and at or after `payment_expires_at` by the **server's** clock (customer app review). A repeat with the same key returns the same gateway order.
  - **Cancel (T5):** PAYMENT_PENDING with no captured payment; releases the reservation and the coupon hold, closes open payment attempts; the cart is kept.
  - **Expiry (T4)**, `expire_unpaid_orders` (beat, every minute): for each order past its window, asks the gateway for captured payments on each of its gateway orders (a missed webhook places the order instead); if the gateway cannot be reached the order is left for the next run; otherwise PAYMENT_FAILED, stock and coupon released.
  - **List** `GET /orders/`: newest first (active first without `status`); a fixed number of queries whatever the number of orders (test-asserted). Domain events (`order.placed`, `order.payment_pending`, `order.payment_failed`, `order.cancelled`, `payment.late_capture`) run after commit as a Celery task that logs them in Phase 3; Phase 4/6 hang notifications on them.
- **Deploy check `payments.E003`** (`check --deploy` only): a staging or production deployment that uses the Razorpay gateway without all three `RAZORPAY_*` keys is an error. A dry run whose `ALLOWED_HOSTS` are all reserved example domains (RFC 2606/6761: `example.com/.net/.org`, `*.example`, `*.test`, `*.invalid`, e.g. CI's `api.example.com`) is skipped, so CI needs no keys. Signatures that are not ASCII are refused as invalid (400), never a 500.
- **Fake gateway "down" switch** (P3-TC-63, Phase 4): with `FAKE_GATEWAY_DOWN=True` (local development only) every call of the fake gateway (create order, verify, list payments, refund, list refunds) raises `GatewayUnavailable`, as if Razorpay could not be reached: `POST /orders/` (ONLINE) and `retry-payment` answer 503 `SERVICE_UNAVAILABLE` with nothing created, `POST /payments/razorpay/verify/` answers 503 (the order stays PAYMENT_PENDING; call verify again), `expire_unpaid_orders` leaves due orders for its next run, and refunds stay PENDING (the task retries). COD is unaffected. The real gateway ignores the setting, and the system check `payments.E004` refuses it in staging and production.

Staff refunds: `manual_refund` (Super Admin and Finance; Support up to `SUPPORT_REFUND_LIMIT` ₹500 per refund) and the ops retry hook `retry_refund` (T-401c: a FAILED refund gets a new attempt; a PENDING one with no gateway answer after `REFUND_STUCK_MINUTES` is sent again).   - **Invoices** (`apps.orders.invoices`): numbered `<store invoice_prefix>/<FY>/<6 digits>` per store and Indian financial year (IST); GST-inclusive prices split per line at the product's rate after a pro-rata share of the coupon; fees at `INVOICE_FEE_GST_RATE`; the tip is outside the invoice; CGST+SGST when the store and delivery states match, else IGST. **D-12 pending:** without a store GSTIN, product HSN or fee SAC the placeholders `GSTIN-NOT-SET`, `HSN-TBD`, `SAC-TBD` are used, `Invoice.is_placeholder` is set and the PDF says "PLACEHOLDER - NOT A VALID TAX INVOICE".
  - **T-403c:** `retry-payment` creates the gateway order outside the order row lock and re-checks under it; `expire_unpaid_orders` runs one at a time (Redis lock, 5 min) and skips orders locked by another worker (`skip_locked`). `process_refund` (P4 review Major 1) checks the refund under the order and refund row locks briefly, then calls the gateway with no lock held and re-locks in `record_refund_status`; one worker per refund at a time is guaranteed by a PostgreSQL session advisory lock (`pg_try_advisory_lock`, released at the end or when a crashed worker's connection closes), backed by the lookup by receipt. **Still open:** placement calls the gateway under the customer's own cart lock (it serialises that one customer's placements; no other customer waits on it). Moving it out needs a re-check of the whole cart after the call, so it is left for a later run.
  - **Acceptance:** a PLACED order schedules `auto_accept_order` (stores with `auto_accept_orders`, after `AUTO_ACCEPT_DELAY_SECONDS`) and `store_acceptance_sla_alert` (after `STORE_ACCEPTANCE_SLA_SECONDS`, 60 s; one alert per order, event `order.acceptance_sla_breached`, logged at ERROR); the beat job `auto_accept_orders` (every minute) catches both if a countdown was lost.
  - **Domain events added:** `order.accepted`, `order.packing`, `order.packed`, `order.items_adjusted`, `order.acceptance_sla_breached` (logged; push/SMS/WebSocket in Phase 6).

## 4. WebSocket endpoints [P6]

Auth: the JWT is sent in the first message after connecting (`{"type": "auth", "token": "..."}`), or as a `Sec-WebSocket-Protocol` value. It is **not** put in the URL query, so tokens don't land in logs. Staff sockets use the Django session.

| Path | Client | Server → client message types |
|------|--------|-------------------------------|
| `/ws/v1/orders/{order_id}/` | Customer (owner) | `order.status`, `rider.location`, `order.eta` |
| `/ws/v1/rider/` | Rider | `offer.new`, `offer.withdrawn`, `task.updated` (e.g., packed / cancelled) |
| `/ws/ops/live/` | Staff | `order.created`, `order.status`, `rider.location`, `rider.status`, `alert` (scoped to permitted stores) |

### 4.1 Connecting (Phase 6, `apps.realtime`)
- **App sockets (`/ws/v1/`):** connect, then send `{"type": "auth", "token": "<access JWT>"}` within `WS_AUTH_TIMEOUT_SECONDS` (10 s). Or offer the subprotocols `["jivo.v1", "jivo.auth.<access JWT>"]`: the server selects `jivo.v1` and never echoes the token. The server answers `auth.ok` with the token's `expires_at`. Before then, send a new auth message with a refreshed token (same user), or the socket closes with 4401. `{"type": "ping"}` is answered with `pong`. There is no Origin check: native apps send none, and the JWT is not ambient, so a cross-site page cannot use it.
- **`/ws/v1/orders/{id}/`:** the order's owner only. Right after `auth.ok` the server sends one `order.status` snapshot. The delivery OTP is never sent on a socket: when `order.status` is OUT_FOR_DELIVERY, re-read `GET /orders/{id}/track/`.
- **`/ws/v1/rider/`:** a token issued to the rider app (`app` claim `rider`) and an ACTIVE rider profile (Phase 5 model; until it is installed every rider socket closes with 4403).
- **`/ws/ops/live/`:** the staff session cookie (the same login as `/admin/` and `/ops/`), an Origin from `ALLOWED_HOSTS`, permission `orders.view_order`, and at least one store in `stores_for(user)` (05 §3). The socket joins one group per permitted store, fixed at connect. It re-checks the session, role and stores every `WS_OPS_RECHECK_SECONDS` (300 s) and closes with 4401/4403 when access is gone, or rejoins the new store list.
- **Close codes:**
  - 4400: the first message is not `auth`
  - 4401: missing, invalid or expired token, or no staff session
  - 4403: signed in but not allowed (no role or store, not an active rider, wrong app)
  - 4404: the order does not exist **or is another user's** (the same code, so ids leak nothing)
  - 4408: auth timeout

  On any close the app falls back to polling (`GET /orders/{id}/track/` every 10 s, `GET /rider/offers/current/`) and reconnects with backoff.
- **Message shape:** every server message is `{"type", "data", "sent_at"}` and carries the current state, not a diff, so a duplicate or missed message is harmless. On reconnect, re-read the REST endpoint. Each message is published in `openapi/schema.yaml` as a `Ws...Message` component with its `Ws...Data` (`apps.realtime.contract`), so the generated client has the models.

Rules for the envelope (implemented in `apps.core.exceptions`, codes in `apps.core.errors.ErrorCode`, published as `ErrorCodeEnum` / `ErrorEnvelope` in the OpenAPI schema; the inner `error` object is the component `ErrorBody`, renamed from `ApiError` in Phase 1 R3 because it clashed with `jivo_core`'s `ApiError`; the JSON shape did not change):
- `details` is always an object, possibly empty. `VALIDATION_ERROR` puts field name → list of messages there, with `non_field_errors` for errors that are not about a field. Malformed JSON is also `VALIDATION_ERROR`.
- `401`: `AUTH_REQUIRED` when no credentials are sent, `TOKEN_INVALID` for a bad, expired or revoked token (or an inactive user).
- Django's `Http404` / `PermissionDenied` / `ValidationError` map to `NOT_FOUND` / `PERMISSION_DENIED` / `VALIDATION_ERROR`. Unmatched `/api/...` URLs also return the JSON envelope.
- Codes are a stable contract: add new ones, never rename or remove.
